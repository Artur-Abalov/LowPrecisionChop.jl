Verification

A package that claims to reproduce another implementation's arithmetic has to show its work. This page describes what the correctness claims rest on: which oracles are used, what each covers, and — just as importantly — what has no oracle at all.

Run everything with Pkg.test(). The third-party integration suites live in separate environments and run independently; see Integration findings.

Oracles

1. The MATLAB reference, transcribed

test_chop.m (602 lines) and test_roundit.m (136 lines) from higham/chop are an unusually convenient oracle: every assertion in them is expressed in closed form — powers of two, xmin/xmax/xmins, eps(single(1)) — rather than as recorded numbers. That makes the whole file computable directly in Julia, with no MATLAB installation required.

Ported as @test cases in test/kernel_matlab_transcribed.jl:

2. Golden values from pychop

test/data/chop_golden.csv holds 2720 rows generated by test/data/generate_golden.py from pychop v0.6.1 (pychop.faultchop.FaultChop — its higham/chop-compatible port, not the separate Chop/LightChop_ class, which uses unrelated mode numbering), NumPy 2.0.2, Python 3.9.13.

Coverage: rounding modes 1–4 only, five formats (fp8-e4m3, fp8-e5m2, fp16, bfloat16, fp32 — the presets pychop shares with this package), both subnormal settings, roughly 68 inputs per combination. The inputs are fixed edge cases (zero, ±1, xmin/xmins/xmax and their neighbours, ±1e±300) plus 40 seeded-random values per combination. Compared for exact equality in test/chop_golden.jl.

To regenerate:

python3 -m venv /tmp/pychop_venv
/tmp/pychop_venv/bin/pip install pychop numpy
/tmp/pychop_venv/bin/python3 test/data/generate_golden.py
pychop is not an oracle for `flip`

pychop's NumPy-backend round_to_nearest helper calls np.random.randint(low=0, high=1, ...), which is half-open [0,1) and therefore always returns 0 — so pychop's flip fires 100% of the time regardless of p, diverging from MATLAB's continuous-uniform ≤ p semantics. flip/p coverage comes from test_roundit.m's own proportion assertions instead.

3. An independent BigFloat oracle

test/kernel_bigfloat_oracle.jl re-implements the same rounding algorithm from scratch at 256-bit precision and checks the Float64 kernel against it for the deterministic modes. This is the only oracle for the three things with no external reference:

  • TF32Format — no reference implementation has this preset;
  • Float64Format — pychop has no equivalent;
  • RoundNearestTiesAway (mode 7) — exists in no reference implementation at all, which is why it is deliberately absent from chop_golden.csv rather than filled in with fabricated expectations.

4. Native Julia types, exhaustively

Because Float16Format, Float32Format and Float64Format are exactly IEEE binary16/32/64, native Julia arithmetic is itself an oracle.

test/kernel_float16_exhaustive.jl checks conversion over all 65536 Float16 bit patterns, then + - * / over representative and random operand pairs, against native Float16. test/native_contracts.jl repeats the exhaustive conversion check through the public API (chop and LowFloat, not the internal kernel) to confirm the wiring, and adds randomized + - * / sqrt checks for both fp16 and fp32.

This exhaustive pass is what caught the subnormal-scale bug documented in Specification §5: a literal translation of chop.m's subnormal branch flushed certain subnormal fp16 products to zero where both native Float16 and the BigFloat oracle agreed they should not.

5. Property-based invariants

test/kernel_invariants.jl asserts properties that must hold regardless of format or mode:

  • idempotence — rounding an already-rounded value changes nothing;
  • sign symmetry for the deterministic modes;
  • bracketing — RoundDown never exceeds the exact value, RoundUp never falls below it;
  • monotonicity — the deterministic modes preserve ordering;
  • grid completeness — nextfloat/prevfloat traverse a tiny format (t=3, emax=3) with no gaps and no duplicates;
  • stochastic reproducibility — same seed, same sequence;
  • flip reproducibility — same seed, same flips; p = 0 never flips.

The stochastic modes get property tests rather than golden values deliberately: pychop's NumPy RNG and Julia's Xoshiro are different algorithms, so "the same seed" does not mean "the same draws", and a CSV row can only encode one arbitrary realization of a rule, never the rule itself.

6. Structural checks

  • test/kernel_allocation.jl — the scalar kernel is non-allocating and type-stable.
  • test/lowfloat_interface.jl — includes the crucial guardrails: LowFloat is not a BlasFloat, and promote_type(LowFloat, Float64) does not resolve to Float64 (either failure would silently bypass the simulation entirely).
  • test/extension_microfloatingpoints.jl — round-trip conversion through the weak-dependency extension.
  • CI additionally runs Aqua.test_all and JET.report_package, with zero tolerated reports.

Paper experiment reproductions

test/paper_experiments.jl reproduces three tables from Higham & Pranesh (2019). These are end-to-end checks: they exercise format, rounding mode and accumulated-error behaviour together against numbers published independently of this implementation.

Table 6.3 (p. C596) — harmonic series ∑1/i across precisions, default round-to-nearest. All four cheap cells reproduce exactly:

formatpublished sumpublished terms
fp8 (Moler's informal t=5, emax=3)3.500016
bfloat165.062565
fp167.0859513
fp3215.4042097152

The fp64 row is not reproduced: the paper quotes it from Malone, from a computation that took 24 days.

Table 6.4 (p. C597) — harmonic series across rounding modes. Four of six rows are deterministic and reproducible: nearest, toward +∞, toward −∞, and toward zero (the paper's own caption notes toward-zero coincides with toward-−∞ in this example). Modes 5–6 depend on MATLAB's own rng(1) stream and cannot be reproduced outside MATLAB.

13 of the 14 deterministic cells across Tables 6.3 and 6.4 match exactly. The one that does not is documented in Known limitations.

Table 6.5 (p. C597) — subnormals vs flush-to-zero on ∑ 1/(n-i+1)² in fp16. The qualitative result reproduces (subnormal support strictly improves accuracy, by a margin growing with n); the exact published digits do not, under either plausible reading of the per-operation rounding sequence. Also documented in Known limitations.

What has no oracle

Stating this plainly is part of the verification story:

thingoracle situation
RoundNearestTiesAwaynone external; BigFloat oracle only
TF32Format, Float64Formatnone external; BigFloat oracle only
stochastic modesno value-level oracle possible; property tests only
flip/pMATLAB's test_roundit.m proportions only (pychop is unusable here)
^, floor/ceil/trunc/round, abs2, invcorrectness-by-construction; the double-rounding proof covers only + - * / sqrt
BFloat16s.jl cross-checkwritten but @test_skip — the package has never been installed alongside this one
degenerate formats (t=1, emax≈0)no dedicated suite; covered only incidentally by random sampling

The full list, including infrastructure gaps, is in Known limitations.

Benchmarks

benchmark/run.jl records timings for the scalar kernel, chop on scalars and arrays, chop! in place, and LowFloat arithmetic and reductions:

julia --project=benchmark benchmark/run.jl

These are recorded, not asserted — there are no pass/fail thresholds, and no comparison against other packages. Treat the output as a reference point for your own measurements.
